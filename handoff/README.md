# 协作流程

这个目录记录每轮的要求、执行证据、复核结论。常驻约束见 [AGENTS](../AGENTS.md)，可改范围与 FE/BE 规则见 [OWNERSHIP](OWNERSHIP.md)，文档职责见 [文档导航](../docs/README.md)。本文件只维护轮次、提交和交班步骤。

## 当前做法

| 做法 | 用在 | 分工 |
|---|---|---|
| **连做** | 008 起到现在 | 同一个助手写 `request.md` → 实现 → `report.md` → **自查**写 `review.md`。用户外出或让助手连续推进时用 |
| **前后端轮流连做** | 270 起 | Claude 前端、GLM 后端；历史 GPT 是后端职责称呼。各自照连做流程走，改动范围和交接规则见 OWNERSHIP；共享检出同一时间只有一个助手在干活 |

**连做的自查不能替代独立复核。** 自查找到过很多真问题，但也判断错过（例子见 `REVIEW-GUIDE.md`）。连做的轮次在 `STATUS.md` 里标「自查通过」，不标「复核通过」，等有人按 `REVIEW-GUIDE.md` 独立复核后，把结论追加到对应轮次的 `review.md`。

## 目录结构

```
handoff/README.md                  本文件：轮次怎么做
handoff/OWNERSHIP.md               可改范围与 FE/BE 交接规则
handoff/STATUS.md                  当前进度，规定下一步做什么（进度只写这里）
handoff/archive/                   退出当前入口的历史状态，不提供当前任务
handoff/REVIEW-GUIDE.md            独立复核指南
handoff/rounds/<序号>-<名字>/
    request.md                     本轮要求
    report.md                      本轮实现报告
    review.md                      本轮复核结果
    其他文件                        可选：脚本、原始输出等证据
```

轮次目录按拉取后的最大号加一，名字用英文小写加短横线。前端用 `NNN-f<阶段>-…`，后端用 `NNN-be-…`，文档/复核等专项用 `NNN-<主题>`。

## 一轮的流程（连做）

1. 接班先 `git status`，干净时 `git pull --rebase`；有他人的草稿就停下问用户。读 STATUS 头部与当前任务表，确认本轮范围；不能从历史「下一步」领取任务
2. 新建轮次目录，写 `request.md`：背景、范围（做什么、**明确不做什么**）、验收标准
3. 读对应设计并实现。需要用户拍板的变化先问，批准后先改对应设计再改代码；现行站/新栈的权威关系见文档导航
4. 在测试机后台跑整组和本轮必要的专项验收（docs/development.md），写 report，记录真实命令、日志编号、退出码；未执行写「未验证」
5. 自查：换个角度重新验证（自己重跑、把实现改坏看测试红不红、对照设计原文逐条核对），写 `review.md`
6. 按 docs/README.md 的职责表更新文档；STATUS 每轮更新当前任务/验收表与摘要。最近轮次最多 3 条，超出的移进 archive，未完成事项继续留在当前表
7. 按下节一个中文提交，提交后 `git pull --rebase`、马上推 `origin main`；检查该提交 SHA 对应的 CI，红了优先修，交班时工作区干净

001–007 的设计/实现分工经过见相关轮次，已经退出当前流程。

## 提交与交班

- 标题为 `NNN: 一句话说改了什么`，中文；空一行后详细写做了什么、为什么改、真实验证及日志编号/退出码，不能只有标题。
- 正文末尾空一行写 `Co-authored-by: 具体模型 <对应平台邮箱>`，按实际运行模型署名，不用公司或平台泛称，不替另一位助手署名。示例：`GPT-6 <codex@openai.com>`、`Claude Opus 5.5 <noreply@anthropic.com>`、`Gemini 3.8 Flash <gemini-code-assist@users.noreply.github.com>`；Cursor 使用 `Cursor <cursoragent@cursor.com>`。GitHub 贡献者列表异步更新，不为头像显示伪造模型。
- 作者沿用仓库本地的 Uniseem noreply 配置，不改身份，不用真实姓名/邮箱。045 以前的英文提交不重写。
- git add 明确列自己范围内的路径，不用 `git add .` 或 `git add -A`。提交后拉取发现轮次号被占用，目录、三份文件标题、STATUS、提交标题一起改成下一个空号。
- 自己的改动提交推送或清掉后交班，不替别人提交或删文件。并行开工需用户授权、各用独立克隆。
- 后台等 CI 时先按当前提交 SHA 取运行 ID，再等该 ID；不要误等上次运行。

## 报告纪律

1. 发现实现与对应设计有偏差，写进 report；权威关系与落笔位置见 docs/README.md
2. **报告里的验收输出必须是真实执行过的命令输出。** 没跑的写「未验证」
3. **每轮结束更新 `STATUS.md`**，一轮一个提交
4. 常驻约束只维护在 AGENTS；验收细节只维护在 docs/development.md，不在报告或流程文档另写一套
5. **不在本轮范围外改动。** 顺手发现的问题写进报告「顺带发现」，由后续轮次处理
6. 范围、设计或必要信息不确定时先查权威出处；需要用户拍板的问用户
7. **历史轮次的文件写完不改。** 后来发现写错了，在原文位置加一段「NNN 轮更正：……」，保留原文。这样能看出当时为什么那样判断
8. **「等某个条件才能做」要先问一句：能不能拆，有没有一部分现在就能做。** 023、034、035、038 都栽在这里

## 文件格式

实际报告可以按内容调整小节，但下面这些信息不能少。

### request.md

```
# <轮次号> <标题>
## 背景        为什么做这一轮
## 本轮范围    做什么 / 明确不做什么
## 任务        逐条，每条带验证方式和期望结果
## 验收标准    要跑哪些命令、期望输出
```

### report.md

```
# <轮次号> 实现报告
## 结论        一句话：完成 / 部分完成 / 未完成
## 逐条结果    对应 request 的每条任务
## 验收输出    真实命令输出
## 设计偏差    和本轮对应设计不一致的地方
## 未完成 / 顺带发现 / 需要确认
## 改动文件
```

### review.md

```
# <轮次号> 复核结果
## 结论        自查 / 独立复核；通过 / 需返工 / 部分完成
## 验证记录    实际跑了什么，结果如何
## 发现的问题  必须修 / 建议修
## 判断里最没把握的
## 文档更新    本轮更新的权威文档与当前状态
```
