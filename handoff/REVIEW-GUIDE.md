# 独立复核指南（008–043、074–079）

写给做独立复核的人（用户计划交给 Grok）。

30 轮各自的 `request.md` 末尾有自己的复核清单，`report.md` 有验收输出，`review.md` 有实现方的自查结论。**但 30 轮逐个读一遍成本很高，而且平均用力等于没有重点。**

这份文件的作用是指路：**哪里最可能还有问题，以及为什么这么判断。**

## 怎么用

1. 先读这份
2. 按下面的优先级挑着查，每条都写明了「怎么验」
3. 结论追加到对应轮次的 `review.md`
4. 不同意实现方的判断时，直接说——下面「实现方的主观取舍」那节就是专门列出来给你推翻的

## 优先级 1：本 session 修过的地方

这些地方刚改过，是最可能有新问题的地方。而且它们之所以有问题，往往说明那一块的测试本来就弱。

| 查什么 | 出处 | 怎么验 |
|---|---|---|
| **字体切片可复现** | 023 A1 | 同一个字体连切两次，内容哈希必须一样。`recalcTimestamp=False` 是关键。**这个 bug 从 013 轮潜伏到 023 轮，表现为「偶发测试失败」** |
| **报名状态机的越权** | 018 A1/A2、067 | 067 删掉了上游审核，只剩管理员审核和「报名自动通过」。值得试：有报名之后能不能从后台改开关（原来的「审核模式」锁只在 API 里拦过，后台从没拦，067 才补）；系统自动通过是不是只发一封邮件；同步名单后会不会再次自动通过 |
| **备份备的是哪个文件** | 022 A1 | `settings.DATABASE_PATH` 和 `connection.settings_dict["NAME"]` 不一定相同。测试环境下就不同 |
| **恢复的顺序** | 022 A2 | 先复制数据库再删 WAL 会让恢复静默失败。把顺序改回去跑测试，应该红 |

| **赛事详情页的查询数** | 034 | 造 200 支通过审核的战队，看查询数是不是恒定 |

## 优先级 2：我自己认下的、测试不够强的地方

这个 session 里**五次**发现「绿灯的测试其实没在测该测的东西」：

| 轮次 | 表面上在验什么 | 实际上验了什么 |
|---|---|---|
| 019 | 接口文档页能用 | 服务端没崩（返回 200，页面是空白的） |
| 021 | 剪枝没改变最优解 | **一个随机种子**下没改变 |
| 023 | 首页体积不超预算 | HTML 不超预算（静态资源全 404 被跳过了） |
| 026 | 邮件主题对 | 主题里有活动标题（前缀重复了也通过） |
| 029 | 地址存在 | `resolve()` 没抛异常——**而 Wagtail 兜底路由让它永远不抛** |

**建议的查法**：挑几条关键测试，把对应的实现改坏，看测试会不会红。这是我后期每轮都做的（「变异测试」），但前期（008–017）没有系统做过。

**039 轮我自己先试了 14 个变异点**（原本想留给你，但那个理由站不住——变异测试的结果是机械的，不受实现方倾向影响）。结果：

- 11 个被抓到
- **3 个连全量回归都抓不到**，已记录在 `039-mutation-sweep/report.md`：预渲染的 Set-Cookie 闸、解散战队仍可申请入队、签名比对不是常数时间
- 另有 2 个是被本 session 后期加的测试救的，说明 008–017 当初确实没覆盖

**14 个远不是全部。** 这条建议仍然成立，只是起点比原来高一些。

**042 轮改成了机械枚举**：`rounds/042-guard-sweep/mutate_guards.py` 找出全部 218 个「条件成立就拒绝」的守卫逐个拆掉。042 跑了 40 个，**059 跑完剩下的 178 个**，218 个全部有结论：补了 84 条测试（051 的 15 条和 059 的 69 条），其余的判为等价、不补或另开一轮，理由在 `rounds/059-guard-sweep-finish/report.md` 的表里。**最值得你质疑的是那 10 个「等价」**，特别是 `core/offsite.py` 的三处，我只读了代码，没构造验证

**064 发现了另一类盲区：只在服务器上才存在的配置。** 测试跑在一个进程里，看不到「哪个容器挂了哪个卷」。worker 没挂静态卷，事件触发的预渲染在测试机上从部署那天起就全部失败，而 053 以后的验证都是在 `web` 容器里跑命令，11 轮没发现。**值得查的**：`deploy/docker-compose.yml` 里每个服务要读写的东西都挂了没有；worker 做的事（邮件、字体处理、预渲染）在服务器上各真跑过一次没有——064 之前服务器上的 worker 只看过心跳（`/healthz`），邮件要等发信服务，字体处理还没在服务器上跑过

## 074–079 前台重做：最值得复核的地方

074–077 把前台整个换成了自己的设计体系（设计 13.2，样张页 `/_styleguide/`，要能进后台的账号），078 收尾，079 调了对比度。**全部是本 session 自查，没有独立复核，也没在真手机上看过。** 服务端测试管得住「用了哪个组件、状态是什么形状」，管不住「排出来好不好看、手机上有没有挤爆」。

**最可能有问题的**

| 查什么 | 出处 | 怎么验 |
|---|---|---|
| **手机上的排版** | 075–077 | 077 用浏览器探针在 360px 下查了 33 个页面有没有元素超出视口（探针见 077 报告），但只在 Linux 的 Chromium 里跑过。值得在 iOS Safari 和微信内置浏览器里过一遍：抽屉菜单（`<details>`）开合、个人中心标签条、赛事和内战的票根、战队报名的名单表格（`c-table--stack` 在手机上变成一行一卡） |
| **预渲染页和占位区域** | 074–076 | 首页、资讯、文章、赛事、内战、战队、成员页是预渲染的，个人相关的部分走 `data-slot`。验：未登录打开预渲染页，Network 面板里不应有任何 `/_fragments/` 请求；登录后只有一次 `/_fragments/state/`，页头不应先闪一下「登录」再变成头像 |
| **内战「报名中」会不会过期** | 076 | 状态写死在静态页上，076 在报名截止和开始时刻给 `/`、`/scrims/`、`/scrims/<id>/` 排了重新生成（`scrims/services.py` 的 `schedule_home_refresh`）。验：造一个 5 分钟后截止的内战，**在服务器上让 worker 跑着**，截止后看三个页面变没变。只在 `web` 里跑通不算（064 的坑） |
| **首页日程带按哪天算** | 075 | 14 天，按上海时区分日。验：23:30 开始的内战、跨月的两周、没有任何内战的两周（日程带照样画 14 天，下面写「未来 14 天还没有安排内战」） |
| **评论区的两套模板** | 075 | 静态页是只读版，登录后换交互版；075 只改了样式类，`hx-*` 没动。验：登录后点赞、回复、切换「最新 / 最热」，排序的隐藏字段还在 |
| **CSP** | 074–077 | 前台不能有内联样式。验：生产配置下浏览器控制台没有 CSP 报错，样张页和首页焦点图都看一遍 |
| **文字对比度** | 074、079 | 074 定的 `ink-3` 只有 3.75:1，078 发现，079 调到 4.85:1，控件边框从 2:1 调到 3.7:1，测试按设计 13.2.3 的组合表逐对计算。测试只管令牌之间的组合；验：用浏览器开发者工具的对比度检查抽查几页，特别是深色区块（页头、赛场、票根、页脚）里的小字和搜索框 |
