# 166 地址里的编号太大、日期太离谱时返回 404 或提示，不再 500

## 背景

继续自主推进。站长看日志的角度：165 之后在测试机上临时写了一个探测，用一堆奇怪的参数访问公开页、个人中心和后台（不存在的分类、负数页码、空字节、超长关键词、20 位的编号、离谱的日期），看有没有 500。大部分都是 200 或 404，有三处 500：

```
PROBE 500 /comments/99999999999999999999/more/          （公开，谁都能打开）
PROBE 500 /admin/announce/article/99999999999999999999/
PROBE 500 /admin/activity/?start=0001-01-01&end=9999-12-31
```

前两个是同一个原因：Django 对超出 64 位整数的主键查询会直接返回「没有」（所以内战、赛事的 20 位编号是 404），但文章的主键是 Wagtail 页面的一对一外键，这层保护不管，SQLite 报 `OverflowError`。第三个是 9999-12-31 加一天溢出。

谁都能用前一个地址制造 500：不危险，但日志里会一直有，监控也会误报。

## 本轮范围

1. 自定义路径转换器 `id`：最多 18 位数字（一定放得进 64 位整数），更长的地址直接不匹配、404。项目里自己的 58 处 `<int:…>` 全换成 `<id:…>`；加一条测试，以后再写 `<int:` 会红
2. 活动数据的日期限定在 2000-01-01 到 2100-12-31，超出时提示并回到本学年
3. 这三个地址各一条测试

## 验证

测试：上面三个地址分别是 404、404、200 带提示；项目代码里没有 `<int:`。变异逐条改坏。

## 验收标准

测试机上整组检查全绿；变异全部被抓到；推送 `main`，CI 绿；演示站升级后公网访问第一个地址是 404。
