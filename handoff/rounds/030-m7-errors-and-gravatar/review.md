# 030 复核结果

## 结论

**通过。** 两件事都做完了。这轮最该记的是**我更正了自己的一个错误判断**。

## 反省：我把「没找到」当成了「不存在」

018 轮我要找 API 错误码总表，去 11.4 看了一眼没有，就在报告里写「设计 11.4 的错误码总表漏了两个码」，并把它挂成待用户拍板的问题。

实际上表在 11.10，而且那两个码好好地在里面。

问题不在于看错了章节号——那是小事。问题在于**我从「我没找到」直接跳到了「它不存在」，还把这个结论写进了要用户决策的清单**。正确的做法是先全文搜一下 `错误码`，五秒钟的事。

代价：这个不存在的问题在 STATUS 里挂了两轮，用户回来还得看一眼、还得回我「你自己看」。

**推论**：报告里凡是写「设计里没有 X」「设计漏了 X」的地方，都该先全文搜一遍再写。我这个 session 写了 13 轮报告，这类断言不止一处。

## 这轮实际找到的问题，价值比原来那个「问题」大

真比对之下，19 个错误码里有 5 处不符——4 个没实现、1 个状态码错。其中两个对上游是实打实的体验差别：

- 拼错展开项名字，原本返回 `403 没有权限`，会让对接方去查授权配置
- 服务器内部出错，原本返回 HTML 错误页，对 JSON API 来说是无法处理的响应

如果 018 轮我真去查了表，这五处当时就能发现。**含糊的「好像漏了」挤掉了本该做的那次比对。**

## 差点被自己弄坏

修的时候我加了一行 `response.status_code = ERRORS[code][0]`，把 DRF 判断出的 403 盖成了 422。019 轮写的两条文档页权限测试当场变红。

这是这个 session 里第一次「旧测试救了新代码」——前面几次都是反过来（新测试发现旧代码的问题）。说明那些测试是有价值的资产，不只是验收时的仪式。

## 认可的判断

1. 把整张错误码表（19 行，码名 + 状态码）写成一条断言。它是对外契约，散在各处断言不如集中钉死。
2. `invalid_include` 的 `details` 里带上全部合法取值。对接方看到「你写的 `menbers` 不在 `[logs, members, members.ranks, team, tournament]` 里」就不用翻文档了。
3. 状态码一律听 DRF 的，只填码名。
