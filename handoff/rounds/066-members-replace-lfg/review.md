# 066 复核结果

## 结论

**通过。**

## 逐项

| 要求 | 结果 |
|---|---|
| 去掉组队大厅 | 应用、页面、片段、后台、游戏模式、设置、功能权限、送审类型、限流、导航入口、脚本、样式、文档都删了；全仓库搜 `lfg`、车帖、发车、游戏模式，只剩有意保留的历史说明和「已删除」的测试 |
| 数据库清干净 | 本地演练和测试机上：旧表、迁移记录、内容类型都是 0 |
| 成员展示所有加入的用户 | 已加入 = 未停用 + 验证过邮箱；测试 + 变异 |
| 分组后台可自定义 | 后台表单端到端测试（新建、拒绝没加入的人、拒绝重复）；内容编辑能管、赛事管理员不能 |
| 不泄露个人信息 | 成员页没有游戏 ID、邮箱、联系方式；有测试 |
| 页面及时更新 | 7 种变化各有测试；登录不触发 |

## 判断里最没把握的

- **「加入的用户」的定义是我定的**：未停用 + 验证过邮箱。如果用户的意思是「加入了社团」（比如只展示交大认证过的、或者只展示在某个分组里的），要改 `members.services.joined_users()` 一处
- **成员页公开给所有人**，包括没登录的访客。昵称和战队本来就公开，但「一份完整的成员名单」比零散的昵称更容易被整体抓取。页顶有测试环境的禁止抓取，正式站 robots 允许抓取。如果社团介意，可以改成登录后才能看
- **没有「我不想出现在成员页」的开关**。用户要求是「展示所有加入的用户」，所以没做。隐私政策里写明了会出现在成员展示页
- 迁移里直接写了 `DROP TABLE` 和改 `django_migrations` 的 SQL。只对「以前装过组队大厅」的库有作用，新库上是空操作；两种情况都跑过（新库是测试用的临时库，旧库是本地样例库和测试机）
- 后台成员下拉框会列出所有未停用的用户（包括没验证邮箱的，选了会在保存时报错）。人多了下拉框会很长，以后可能要换成搜索选择
