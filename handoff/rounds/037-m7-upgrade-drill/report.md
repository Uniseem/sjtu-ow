## 补的缺口：恢复了旧数据库，但代码还是新的

设计 16.8 第 8 步写的是「恢复第 2 步的备份，**切回旧镜像**」。

切镜像命令管不了，但**「你现在的数据库比代码旧」这件事命令能看出来**。不看出来的后果是：

- Django 启动不报错
- `/healthz` 也是绿的（它查的是能不能读写，不是 schema 对不对）
- **要等某个请求碰到缺失的列才炸**

而这发生在回滚过程中——你刚经历一次失败的升级，正在手忙脚乱地确认系统恢复了没有。这是最不该出新问题的时刻。

现在 `restore` 会比对迁移状态：

```
=== 回滚：恢复那份升级前的备份，但代码还是新的 ===
  恢复完成。
  注意：恢复的数据库比当前代码旧，还差 1 个迁移（scrims.0001_initial）。
  如果这是升级后的回滚（设计 16.8 第 8 步），**要切回旧镜像**，不要用当前代码继续跑——
  schema 对不上，出问题时才会报错。
  如果你确实想让当前代码用这份数据，执行 manage.py migrate。
```

给出了具体缺哪个迁移，以及两条出路（切旧镜像 / 就地 migrate），而不是只说「有问题」。

schema 一致时不会多说一句话。

## 演示这个提示时先搭错了场景

第一次演示，我把当前库的迁移记录删掉，然后恢复备份——**警告没出现**。

原因：备份是在删除之前做的，**备份里有那条记录**，恢复反而把它补回来了。这个场景根本不是「数据库比代码旧」。

要真正复现，得让**备份本身**缺那条迁移：先删记录 → 做备份（此时备份不含它）→ 把当前库恢复成有记录的状态 → 再从那份备份恢复。这样才等价于「升级时加了迁移，回滚到升级前」。

记一笔：**演示一个警告时，要先确认自己搭出来的场景真的会触发它**。第一次没出现，我差点以为是代码写错了。
