## 自查中发现并已修掉

### A1 字体切片不可复现（真实产品缺陷，从 013 轮潜伏至今）

详细过程写在 `report.md`，这里只记教训。

`test_reprocess_clears_old_slice_files` 在 013 轮偶尔失败，我当时没查出原因，在 review 里写了：

> 如果再次出现，必须查清楚，不要当成噪音。

这轮全量回归时它又失败了。我先按「测试互相污染」的方向查了两个假设：

1. **`--reuse-db` 留下了上一轮中断时提交的行** —— 直接往 `test.sqlite3` 注入一行 `status=processing` 的 `FontFace` 再跑，**测试照样通过，而且注入的行被清掉了**。假设证伪。
2. **别的测试泄漏了 PROCESSING 状态** —— 看起来合理（`another_face_is_processing()` 确实查全表），但没有证据。

两个假设都不对。于是不再猜，改成**在循环里跑全量直到复现，并打出完整 traceback**。复现出来的信息一句话就定了性：

```
At index 0 diff: 'fonts/9002/400-000.900391ef.woff2' != 'fonts/9002/400-000.7b888487.woff2'
```

同样的输入，两次切片得到不同的内容哈希。逐字节 diff 定位到 `head` 表的 `modified` 字段差一秒——fontTools 在 `save()` 时默认重写这个时间戳。

**影响远超一个测试**：分片文件按内容哈希命名，所以每次重新处理字体都会生成全新的一整套分片、把旧的排进删除队列、重新生成 CSS，**让所有访客重新下载整套字体**。中文字体几 MB，服务器在海外。009 轮做的内容哈希去重，在「重新处理」这条路径上从来没生效过。

修法一行：`TTFont(..., recalcTimestamp=False)`。

**教训**：

- **「偶发失败」这个词本身就是一种逃避。** 它要么是测试的问题，要么是产品的问题，没有第三种。这次是后者，而且是个不小的后者。
- **猜假设很便宜，验假设才值钱。** 我先猜了两个「测试污染」的假设，都挺像那么回事，都错了。真正解决问题的是「循环跑到复现，看真实的失败信息」——那条 diff 信息直接指向答案。早这么做能省掉两轮猜测。
- 013 轮我给这个测试加了 `assert ... == "done"` 来排除 requeue 的干扰。**那个改动是对的**：它把失败挡在了更靠近真相的位置，这次才能一眼看出问题不在 requeue 而在路径本身。

### A2 首页体积测试是假的

第一版：

```python
asset = client.get(path)
if asset.status_code != 200:
    continue          # ← 抓不到就跳过
```

开发环境下静态文件不由测试 client 提供，五个资源全 404，**于是这个测试只量了 HTML：1.9KB，远低于 300KB 预算，绿灯**。

一个「只量了 4% 的内容」的预算测试，比没有测试更坏——它给人一种已经守住的错觉。

改成用 staticfiles finders 从磁盘读，**找不到就断言失败**，并且额外断言「首页至少引用了 3 个 CSS/JS」，防止将来引用方式一变又悄悄退化成只量 HTML。改完实测 59.6KB。

这和 019 的 A2（文档页返回 200 但整页空白）、021 的 A2（穷举对比只用一个种子）是同一类错误，**第三次了**：断言的对象不是真正要保证的那件事。

### A3 022 的写入线程可能活过自己的测试

022 那个「边写边备份」的测试起了一个后台线程，`join(timeout=10)` 之后就不管了。如果它没在超时前停下，会**带着数据库连接继续往后面的测试里写行**——这正是最难查的那种污染，而我刚花了很大力气查一个类似的问题。

改成 `daemon=True`，并在最后断言 `not worker.is_alive()`。

### A4 N+1 检查完全缺失

设计 15.1 白纸黑字：「列表页注意避免 N+1 查询……**开发时开启查询计数检查**」。

实际上一条都没有。补了 5 个页面的检查，写法是「数据量从 3 条加到 10 条，断言查询数不增长」，而不是断言某个固定数字——固定数字会因为无关改动天天红，最后被人加 `# noqa` 或者直接改大，等于没有。

验证这套检查真的有用：去掉 `scrims/views.py` 里的一个 `select_related`，测试立刻报

```
/scrims/39/：3 条数据用了 8 次查询，10 条用了 14 次——查询数随数据量增长，说明有 N+1。
```

## 明确不符合的两条

1. **备份未加密就没法外传**（15.2、15.4）。022 已经记为上线阻塞项，这轮只是再次确认。
2. **AI 审核记录「已处理 180 天后删除」没实现**（15.5）。清理任务根本不碰审核记录，所以「未处理的一直留着」这半自然成立，另一半没有。

第 2 条我**没有顺手加**：「已处理」以哪个字段为准（`checked_at`？人工处理完的标记？）要对着设计 5.5 再确认，而这轮的任务是审计不是开发，边审边改容易把审计本身做脏。已经加了一条测试固定住「不删未处理的」，180 天那半列进待办。

## 认可的判断

1. N+1 测试用「数据量翻倍、查询数不变」而不是固定数字。
2. 15.5 的访问日志和应用日志判为「不适用」——它们由 Caddy 和 Docker 的日志轮转负责，不是应用代码能保证的事，硬写个测试是自欺。
3. 响应时间目标判为「未验证」而不是「符合」。开发机上的数字对「海外服务器 + 国内访问」没有参考价值。
