## 必须修（转 009 的 T0）

### A1 重复上传同一字重会留下旧的原始文件

同一 (字体, 字重, 样式) 再传一次时，`add_face_from_bytes()` 用 `update_or_create` 复用同一行，然后 `original_file.save()` 换成新文件名，**旧文件没人删**。中文字体一次就是 8MB 以上，反复调整字重会把磁盘吃掉。

实测：

```
第一次: fonts/5/original/v1.ttf
第二次: fonts/5/original/v2.ttf
磁盘上的文件: ['fonts/5/original/v1.ttf', 'fonts/5/original/v2.ttf']
同一条记录: True
```

修：换文件前先删旧的原始文件。

### A2 「跟随正文」用到的字重可以被删掉，而且删完不重新生成样式表

`services.is_face_in_use()` 只查 `mode=custom` 且 (family, weight) 匹配的区域，但生成样式表用的是 `css.used_pairs()`（会把「跟随正文」解析到正文字体）。两处口径不一致，结果：

```
h1: inherit 700
样式表里 @font-face 数量: 4（400 + 700）
is_face_in_use(700 面) = False   ← 应该是 True
删除后 700 面还在吗: False
```

删掉之后 `media/fonts/<id>/700-*.woff2` 全没了，但**线上那份 `fonts.<hash>.css` 还在引用它们**，用户会拿到一串 404，标题退回假粗体。

修两处：`is_face_in_use()` 改用 `used_pairs()` 的口径；删除字重成功后重新生成样式表。

### A3 新字重处理完不会自动生效（同一个口径问题）

`run_face_processing()` 末尾也是 `if is_face_in_use(face): regenerate_font_css()`。管理员先把正文设成某字体、再补传 Bold，处理完**样式表不会更新**，必须手动再保存一次排版设置。008 验收时我正是手动又保存了一次才看到 700 生效，当时没意识到这是缺陷。

### A4 Google Fonts 重新导入同一字体时，旧分片不删

`add_google_faces()` 用 `update_or_create` 覆盖 `slices` 字段，但旧的分片文件留在磁盘上。同一个字体重复导入会越堆越多（一次 5.9MB）。代码检查确认，未实测（要走外网）。

## 建议修

- **B1** 重新处理成功后立刻删除旧分片。已经加载了旧样式表的页面会拿到 404。样式表本身留了一天，分片应该同样宽限一天。
- **B2** `next_css_name()` 取「现有最大编号 + 1」，两个管理员同时添加字体会撞 `css_name` 唯一约束，报 500。改成撞了就重试，或者直接用主键。
- **B3** 字体库没有显示每个字体占多少磁盘（原始文件 + 分片）。一个中文字体两个字重就是 24MB，海外小机器需要看得见。用户提问里也有这一条。
- **B4** 排版设置的字体下拉只过滤「有处理完成字重的字体」，但如果某个区域已经选了某字体、之后这个字体的字重被删光，界面上会显示一个不在选项里的值。加一条保存时的校验更稳。

## 认可的判断

- 常用汉字用 GB 2312 一级字判定、片内按码位排序：没有频率表就不编，取舍和实测数据都写进了设计 13.12.2 / 13.12.5，做法正确。
- 「跟随正文」缺字重只警告不拦截：硬拦会让「先传 Regular」这个最常见的流程直接卡死。
- 工具类区域只在自定义字体时写 `font-weight`：否则会盖掉模板里的 `font-semibold`，属于回归。
- 切片丢 hinting（小 12%）、Google 分片按内容哈希去重（省一半磁盘）、带哈希的字体文件一年不可变缓存：都合理，已进设计。
- 后台用自定义页面而不是 `ModelViewSet`：一个字体多个字重 + 三条添加路径，通用表单套不进去。
