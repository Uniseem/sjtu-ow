## 结论

**完成，设计 12.12 的断言成立。** 用真线程验证了 IMMEDIATE 事务确实串行化写入，四种并发场景结果都正确。

**没有发现问题**——但这轮的价值不在于"没问题"，而在于把一条一直只是"设计上应该如此"的话变成了可观测的证据。

## 034 的教训用了第二次

034 我推翻了 023 的「性能要等真机」，结论是「等某个条件」的理由要先问能不能拆。

然后 034 自己的报告末尾我写了：

> **并发**。设计假设同时在线 200 人，这轮是单线程顺序请求，没有测并发下的 SQLite 写锁表现。这个值得在试运行时看。

**同样的毛病。** 并发下的吞吐和延迟确实要真机，但并发下的**正确性**——两个请求会不会同时通过检查——本地起两个线程就能测，而且这才是真出事会出大事的部分（一个玩家同时在两支队的名单里）。

所以这轮把它拆开做了。

## 最有说服力的一段：串行是可以看见的

写了个探针，在「检查」和「写入」之间插一个 150ms 的停顿把竞争窗口撑开，记录两个线程的时间线：

```
时间线（毫秒）:
      0.0  线程2  进入 submit
      0.1  线程1  进入 submit        ← 两个线程相差 0.1ms，确实在抢
      5.0  线程2  检查完成
    179.8  线程2  离开 submit
    217.0  线程1  检查完成            ← 等了 212ms 才轮到它
    375.2  线程1  离开 submit

结果: {2: '成功', 1: 'RegistrationError: 共享玩家 已经在该赛事的战队「探针战队2」名单中'}
共享玩家在几份有效名单里: 1
两个线程的 submit 区间是否重叠: True
```

三件事一眼可见：

1. **两个线程确实在竞争**——相差 0.1ms 进入，区间完全重叠
2. **线程 1 的检查被卡了 212 毫秒**——它拿不到写锁，只能等线程 2 的事务结束。这就是 IMMEDIATE 整库写锁，也正是设计 12.12 说的「同一时间只有一个写事务在执行」
3. **串行之后应用层检查正常工作**——线程 1 报的是友好提示「已经在该赛事的战队『探针战队2』名单中」，不是数据库的 `IntegrityError`

第 3 点值得单独说：设计 8.3 写的是「应用层先查一次给友好提示，数据库唯一约束兜底」。因为写入被串行化了，**后到的那个请求看到的是已经提交的状态，所以走的是应用层那条友好路径**，兜底根本没被用上。这比"靠数据库报错"的体验好得多，而且是 IMMEDIATE 带来的。

## 四个场景

| 场景 | 结果 |
|---|---|
| 两个队长同时为同一玩家报名 | 只有一个成功；玩家在**恰好一份**有效名单里；只有一条报名记录 |
| 战队剩一个位置，两个申请同时批准 | 只进去一个；最终 3 人，不超员 |
| 写事务进行中读数据 | 不阻塞，5 秒内读完（WAL 生效） |
| 十个队长同时提交 | **十个全部成功**，没有超时错误 |

最后一条是关于 `timeout=5` 的：整库写锁在十个并发提交下**表现为排队而不是报错**。如果 timeout 太短或锁行为不对，会看到 `database is locked`。

## 另一个变异测试

把应用层的「已在别队名单里」检查整个去掉，只留数据库唯一约束：

```
1 passed
```

**兜底确实是兜得住的**——真并发下，就算应用层检查完全失效，数据库约束也能保证玩家只在一份名单里。这验证了设计 8.3「数据库的唯一约束兜底，防止并发提交时出现漏网」那句话。
