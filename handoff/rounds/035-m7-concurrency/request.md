# 035 并发：验证 IMMEDIATE 事务真的串行

034 的教训是「等某个条件」的理由要先拆开看。034 末尾我写「并发仍然没验证，值得在试运行时看」——**这句话可以再拆一次**：

- 并发下的**吞吐和延迟**要真机和真实负载
- 但并发下的**正确性**，本地起线程就能测

设计 12.12 有一条很具体的断言：

> 所有写事务以 `IMMEDIATE` 模式开启……因此「先检查再写入」的操作天然是串行的，**不会出现两个请求同时通过检查**

015 轮测了「数据库唯一约束兜底」，但用的是**顺序调用两次**——那种测法就算完全没有锁也会通过，它根本没碰到这个断言。

## 任务

用真线程、真连接测这几条：

1. **两个队长同时为同一个玩家报名** → 只有一个成功，玩家只在一份有效名单里
2. **战队只剩一个位置，两个申请同时批准** → 只进去一个
3. **写事务进行中，读不被阻塞**（设计 12.13 说 WAL 读写互不阻塞）
4. **十个队长同时提交** → 全部成功，不出现超时错误（timeout=5 应该是排队而不是报错）

## 关键要求

**必须证明线程真的重叠**，否则测试一前一后跑完也会通过，等于没测。

## 验收标准

1. `ruff` / `pytest` / `makemigrations --check` / 生产 `check --deploy` 干净
2. 贴出证明线程重叠的时间线
3. 清理验证数据
4. git 提交，信息以 `035:` 开头
