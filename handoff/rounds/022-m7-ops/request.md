# 022 上线准备：备份、恢复与运维命令

M7 的第一部分。设计 16.5 和 16.7 要求的命令一个都还没有——019 写 `deploy/crontab.example` 时只能把三条注释掉，这轮补齐。

**M7 剩下的部分**（视觉风格定稿、用户协议和隐私政策正文、生产部署、国内网络访问测试、试运行）**要么依赖用户拍板，要么必须在真实服务器上做**，不在这轮范围内。

## 范围

设计 16.5（每天 04:00 / 04:20、每周日 04:30）、16.7（备份与恢复）、16.8（升级流程里可以脚本化的部分）。

## 任务

### T1 `manage.py backup`

设计 16.7：

1. **用 SQLite 的在线备份 API**生成快照——不能直接复制正在使用的数据库文件（有 WAL，直接复制会拿到不一致的状态）
2. 压缩后连同 `media` 目录一起放进 `backups` 目录，**保留最近 14 天**
3. 输出备份文件路径和大小

注意：
- 备份里有用户邮箱和联系方式。设计说同步到站外之前**要先加密**。这轮**不做**对象存储上传（没有凭据也没法验证），但要把「这个文件没加密，不要直接传出去」写进输出和文档。
- `static` 和 `prerendered` 不备份（可以重新生成）。
- 加 `--keep-days` 和 `--output` 参数。

### T2 `manage.py restore`

设计 16.7 的恢复步骤里能脚本化的部分：

- 从备份文件恢复数据库和 media
- **删除旧的 WAL 文件**
- **清空 `prerendered`**（否则恢复后的数据和旧静态页面对不上）
- 检查 `FIELD_ENCRYPTION_KEY` 是否和备份时一致——**对不上要明确报错**，不要恢复出一堆解不开的密文
- 必须 `--yes` 才真的执行，默认只打印要做什么

停止和启动服务不是 Django 命令能做的，输出里要提示。

### T3 `manage.py cleanup_static`

设计 16.5 每天 04:20：清理 `static` 数据卷里**不属于当前版本、且超过 30 天**的旧文件。升级时新静态资源会加进去、旧的保留（16.8 第 5 步），所以要按 manifest 判断哪些还在用。

### T4 `manage.py optimize_db`

设计 16.5 每周日 04:30：`PRAGMA optimize`。顺带报告数据库大小和 WAL 大小。

### T5 crontab 与文档

把 019 注释掉的三条放开，README 写清楚备份策略、保留期、加密要求和恢复步骤。

## 测试要求

至少覆盖：备份能生成可用的快照（**恢复后数据对得上**）、备份包含 media、14 天保留（旧的删掉、新的留着）、`--keep-days` 生效、**在有活跃写入时备份仍然一致**（这是用在线备份 API 而不是复制文件的理由）、恢复会清空 prerendered、恢复会删 WAL、`FIELD_ENCRYPTION_KEY` 不一致时拒绝恢复、不带 `--yes` 不会动任何东西、`cleanup_static` 只删旧的且不删当前版本在用的、`optimize_db` 能跑通。

## 验收标准

1. `ruff` / `pytest` / `makemigrations --check` / 生产 `check --deploy` 全部干净
2. **真做一次完整的备份恢复演练**：造数据 → 备份 → 破坏数据 → 恢复 → 验证数据回来了。贴出每一步的输出
3. 贴出备份文件的实际大小和目录结构
4. 贴出 `FIELD_ENCRYPTION_KEY` 不一致时的报错
5. 贴出 `cleanup_static` 和 `optimize_db` 的输出
6. 回归 + `docker build` + `caddy validate`
7. 清理验证数据，**并查一次全库计数确认干净**
8. git 提交，信息以 `022:` 开头

## 复核清单（给 Grok）

1. 备份真的是在线备份吗？在写入过程中备份，恢复出来的库是一致的吗？
2. 恢复之后，加密字段（SMTP 密码、API Secret、Webhook 密钥）还能解开吗？
3. 恢复忘了清 prerendered 会怎样？命令有没有真的清？
4. `cleanup_static` 会不会误删当前版本还在用的文件？
5. 备份文件里有没有不该有的东西（比如 `.env`）？有没有明确提示「未加密」？
