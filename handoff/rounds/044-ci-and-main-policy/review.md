# 044 复核结果

## 结论

**部分完成，符合 request 事先划定的范围。** `/healthz` 503 留到 045，理由成立：没有证据时改阈值会让 CI 变绿但可能藏住真问题。

## 这轮最值得记的

**42 轮的「CI 全绿」没有一次是真的 CI。** 每轮报告里的验收命令都照着 `ci.yml` 跑，结果都是真实输出——但跑在我这台机器上。`ci.yml` 本身从来没被执行过，所以它**少了一步 Tailwind 编译**这件事，42 轮都没人知道。

这和 039–042 的变异测试发现的是同一类：**验证的形式对了，但验证的对象不是它声称的那个。** 「测试是绿的」没说是哪个测试；「CI 是绿的」没说是哪台机器。

以后报告里写「CI 全绿」要分清：本地跑的同组命令，还是 GitHub 上的 run（贴 run 编号）。

## 一个差点做错的决定

看到 503，第一反应是「GitHub 机器磁盘满，把测试里的阈值调低」。这很可能是对的，而且一行就能让 CI 变绿。

没这么做，因为：

- 证据只有「本地 28.9%，托管机器通常比较满」，是推测
- 如果原因其实是数据库探活在慢机器上超时，调阈值会让 CI 变绿，**而生产环境的健康检查在慢机器上会误报 503**——这正是 003 轮修过的那类问题
- 多推一次拿到确切输出，成本是几分钟

## 判断里最没把握的

- **Tailwind 编译在 CI 上能不能跑通**：`download_cli` 要从网上下载二进制。`Dockerfile` 也这么做，但 `docker build` 这一步在 CI 里从来没走到过（前面的测试步骤先失败了），所以**这条路在 CI 上同样没被验证过**
- **`docker build` 本身**：同上，CI 里从没执行到
