## 自查中的反省：第四次同类错误

这轮发现的问题，020 的测试本该抓住：

```python
assert scrim.title in mail.outbox[0].subject
```

主题是 `内战提醒：周五内战` 还是 `[SJTU OW] [交大守望先锋] 内战提醒：周五内战`，这条断言都通过。

**这已经是同一类错误的第四次**：

| 轮次 | 表面上在验什么 | 实际上验了什么 |
|---|---|---|
| 019 | 接口文档页能用 | 服务端没崩（200） |
| 021 | 剪枝没改变最优解 | 一个随机种子下没改变 |
| 023 | 首页体积不超预算 | HTML 不超预算（静态资源全 404 被跳过） |
| 026 | 邮件主题对 | 主题里有活动标题 |

四次的共同点：**断言的是「容易断言的东西」，不是「真正要保证的东西」**。而且四次都是绿灯，绿灯本身没有给出任何信号。

能总结出的做法：

1. **写完断言问一句「如果这件事坏了，这条断言会红吗？」**——四次里只要问了，都能当场发现。
2. **对关键的断言做一次变异测试**，成本很低。020 做了变异测试，但只对「角色限定的段位校验」等三条做了，没对邮件那条做。
3. **能扫描的就扫描**，别逐个断言。这轮加的「所有 `notifications*.py` 里主题字面量不许以 `[...]` 开头」比逐封信断言更管用——它管住了以后新写的通知。

## 认可的判断

1. 把附录 C 写成三组测试（`settings` / 代码常量 / `SiteSettings`），而不是一个大字典。三组的失败信息各自指向该改的地方。
2. 主题前缀用扫描式断言而不是逐封信断言。以后新加通知自动被管住。
3. 明确列出「不适用」的几行并说明理由（服务器地区、allauth 默认值、Caddy 配置、cron），而不是假装全覆盖。
