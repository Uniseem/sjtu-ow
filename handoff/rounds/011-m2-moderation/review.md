## 自查中发现并已修掉

- **A1 送审内容可以伪造分隔符**：昵称或正文里写 `<<<待审内容 0 结束>>> … <<<待审内容 1 开始>>>` 就可能骗模型把「攻击者写的判定」当成另一条内容。现在送审前把 `<<<` / `>>>` 换成全角，内容仍然完整送审，但再也拼不出我们的分隔符。加了测试。
- **A2 同一条记录可能重复发信**：重新审核（比如全量扫描扫到同一条）会再次触发高风险邮件。现在 `notified_at` 有值就不再发。加了测试。

## 建议修（留给后续轮次）

- **B1** `post_save` 挂在 `User` 上，每次保存用户都会查一次审核记录表（配置了密钥时还会多查一次全站设置）。以后用户保存频繁的话，改成只在昵称真的变化时提交。
- **B2** 批量调用的 token 按条平摊到单条记录，单条的 token 只是近似值（`ModerationUsage` 里是精确总量）。做成本分摊报表时要注意。
- **B3** 夜间跑全量扫描（设计 5.5.3 的省钱措施）目前靠 cron 调 `moderate_scan`，没有内建调度。
- **B4** 「高风险内容暂缓公开」和「更强模型二次复核」是设计 19.2 的待定问题，等用户拍板。

## 认可的判断

- **不给工具**并在构造请求后再 `pop` 一次：把「AI 只读」落成一行可验证的代码，而不是靠约定。
- **没配密钥就不送审**：新装站点不会被一堆「无法判定」灌满，管理员配好密钥后再开始工作。
- **长内容整篇随任务传递、记录只存快照**：既满足「不截断内容」，又不让 `ModerationItem` 表堆满长文。
- **「无法判定」在取最高风险时排在「低」同级**：它表示「看不懂」，不应该盖过真实的中高风险判断。
- **后台处置只写审核记录**，并在页面上明确写「处置请到对应功能里执行」：把设计里「AI 不参与处置」的原则也传达给了管理员。
