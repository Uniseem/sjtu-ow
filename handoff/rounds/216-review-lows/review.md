# 216 自查

连做轮次的自查，不代替独立复核（`handoff/README.md`）。这一轮测试分给五个子代理写（各自只新建测试文件），它们的报告里对修复本身提过的意见都在下面处理了。

## 换个角度重新验证

1. **子代理当了第二双眼睛**：四块测试的子代理各自把修复整个退回到改之前的版本跑过（不是只靠我写的变异），对应的测试都红了；它们同时指出了三处修复本身的问题，都改了：
   - 字体下载的固定地址连接在设了 `HTTPS_PROXY` 时会去检查代理的地址、拿代理的名字核对证书 → 走代理时检查目标主机，交给标准库建隧道，补了测试
   - D5 只管了「写结论」，没管「记失败」：失败次数会记到已经换成新文字的那一行上，新文字可能因为旧文字的失败被提早放弃 → `note_failure` 同样按 `text_hash` 写；巡查也只数真写进去的结论
   - T3 的写法别扭（拿一个占位字符串转一圈）→ 直接用 `as_id` 的结果；个人报名的 `_own_account` 也改走 `as_id`
2. **变异**：43 处，第一次两处没抓到，都查明了原因（一处是变异脚本改错了地方，一处是测试太松），改完重跑都红。
3. **只用超管测权限的坑**：A2 用内容编辑测（有验证过的邮箱）；B10 的子代理发现「只能添加不能发布」的测试用户不能有验证过的邮箱——验证过邮箱会被自动放进投稿者组，投稿者能发布，测试会因为别的原因变绿。
4. **C10 的演练自己也错过两次**（见报告）：一次是 `docker top` 的参数，一次是空数据卷会被 Docker 按镜像改回属主。第二个错如果没查清，会得出「交接这一步可有可无」的错误结论；正式站的卷都不是空的，交接是必要的。

## 自己挑的毛病

- **B8 的「新建只建一次」靠缓存记钥匙**（数据库缓存，24 小时）。缓存被清掉的那一刻正好碰上重试，还是会多建一条——概率极低，结果也只是多一条草稿（7 天后被清理）。
- **B8 的空草稿清理会删数据**：条件很窄（从没发布、标题摘要正文都空、7 天没动），赛事还要求从没发布过、内战要求没人报名。有一个字的都留着。
- **A10 把限流计数放进事务**：IMMEDIATE 下这是一次写锁，每个被限流的请求多一次很短的写事务；本来 `DatabaseCache` 的 `add` 和 `set` 就是写，代价没变多少。
- **T7 把「已结束」也拦了**：管理员结束以后想补一个驳回（比如发现作弊）就做不了。取舍是不让结束后的操作发出和事实不符的信；真要改记录可以走 `/wagtail/`（超管）。
- **B11 的 30 分钟只管「通知全体成员」**，不管「通知报名的人」：后者常用于更正时间，要能马上再发。
- **日历版本号从 0 开始、0 时签名和以前一样**：已订阅的手机不受影响。代价是 `user_for` 要同时认两种签名内容。
- **F8 的 JS 改动（S8、B5、F5、F9）仍是子串守卫**：逻辑错了抓不到。行为靠 `journey.py admin`（分队页）和 `journey.py`（自动保存）走一遍；S8 的「两张表单真同时在飞」这种时序问题浏览器旅程也不一定碰得到，没有专门构造。

## 结论

自查通过。
