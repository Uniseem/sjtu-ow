# 042 守卫语句的系统变异

## 背景

039 手挑了 14 个变异点，找到 3 个空白。041 补的时候发现 039 对其中一个的描述两处都错了（位置、数量），原因是**变异的名字是我起的，实际改到哪里没对过**。

另外 039 表里最后一行「不限制每人最多当几个队长 —— 找不到对应代码，没测成」**也是错的**：`teams/services.py` 的 `max_captained()` 就是，创建和转让两处都检查。当时是搜索词没对上。

手挑有两个问题：挑哪些带着我的判断；挑的时候靠印象定位。**这轮改成机械枚举。**

## 任务

写一个脚本，用 `ast` 找出业务代码里**所有「条件成立就拒绝」的守卫**：

- `if 条件:` 的直接子语句里有 `raise`
- `if 条件:` 的直接子语句里有 `problems.append(...)` / `errors.append(...)`（报名校验是收集问题再统一抛）

逐个把条件换成 `False`（等于拆掉这道闸），跑测试，看红不红：

1. 先跑本应用的测试，`-x` 遇红即停
2. 本应用测试没抓到的，再跑全量
3. **每个变异点打印 `文件:行号 函数名` 和原条件的源码**——不打印自己起的名字

范围：各应用的 `services.py`、`views.py`、`forms.py`，以及 `registration.py`、`review_admin.py`、`api.py`、`api_views.py`、`webhooks.py`、`signing.py`、`middleware.py`、`prerender.py`、`net.py`、字体的下载/处理/服务、审核的 provider、内战分队页、备份恢复命令。**宁可多不可少**——少了就又回到手挑。

为了在合理时间内跑完，脚本把仓库导出成几份独立副本并行跑（每份自己的测试库）。**并行会让机器变忙，时间敏感的测试可能因此偶发失败，把本该幸存的变异误判成「被抓到」**——所以先在同样的并行负载下跑一遍没变异的基线，并记录每个「被抓到」是哪条测试红的。

## 对幸存者的处理

每个幸存的变异点逐个判断：

- **真空白**（设计有要求、没测试）→ 补测试，变异确认咬得住
- **等价变异**（拆掉也不改变行为，比如前面已经有别的检查拦住）→ 记下理由，不补
- **防御性代码**（正常路径到不了）→ 按 041 的判断，能构造就补

## 验收标准

1. 脚本放在本轮目录，能复现
2. 全部变异点的结果表写进报告，实际输出，不手改
3. 幸存者逐条有结论
4. `ruff` / `pytest` / `makemigrations --check` / 生产 `check --deploy` 干净
5. 源码全部还原（`git diff` 只有测试和文档）
6. git 提交，信息以 `042:` 开头
