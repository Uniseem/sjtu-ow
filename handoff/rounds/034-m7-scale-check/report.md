# 034 实现报告

## 结论

**完成，找到并修掉一个 N+1。** 赛事详情页在 200 支战队时要发 **105 次查询**，改成注解之后是 **5 次**，页面快了 3 倍。

其余各项都在设计目标之内，而且查询数不随数据量增长。

## 先纠正我 023 轮的一个判断

023 轮核查第 15 章时，性能目标那几行我写的是「**未验证**——需要真实服务器和真实负载，开发机上量没有意义」。

**这话只对了一半。** 网络延迟确实要真机量，但：

1. **服务端处理时间在本地量是有意义的**，它把我们的代码和网络分开
2. 更要紧的是，**查询数在本地量和在生产量是一样的**——而查询数才是会随数据量爆掉的东西

结果就是这轮量出了一个 105 次查询的页面。如果一直按「等真机再说」放着，它会带到线上。

```
  ✓ 赛事详情（200 支队）            p95  12.9ms  中位 12.8ms  查询 105   ← 问题在这
  ✓ 内战详情（100 人报名）           p95   4.7ms  中位  4.4ms  查询   4
  ✓ 战队列表（200 支）             p95   6.2ms  中位  6.0ms  查询   3
  ✓ 首页                       p95   2.6ms  中位  2.4ms  查询   7
  ✓ 状态片段 /_fragments/state/  p95   0.8ms  中位  0.7ms  查询  12
  ✓ 组队大厅片段                   p95   0.4ms  中位  0.4ms  查询   1
```

**每一项都在目标之内**——但赛事详情页的 105 次查询是个信号：100 支通过审核的战队 + 5 次基础查询。

## 找到的 N+1

`tournaments/services.py` 的 `approved_teams()`：

```python
for registration in registrations:
    entries.append({
        ...
        "member_count": registration.members.count(),   # ← 每支队一次查询
    })
```

改成注解：

```python
.annotate(roster_size=Count("members"))
```

修完：

```
  ✓ 赛事详情（200 支队）   p95  4.2ms  中位  3.8ms  查询   5
```

**105 → 5 次查询，12.9ms → 4.2ms。**

### 为什么 023 轮的 N+1 测试没发现

023 轮我给 5 个页面加了「数据量从 3 加到 10，查询数不增长」的测试。**赛事详情页不在那 5 个里面**——我测了 `/tournaments/`（列表），没测 `/tournaments/<id>/`（详情）。

列表页显示的是赛事，详情页显示的是**报名的战队**，两者的数据量来源完全不同。我当时按「页面」列的清单，而不是按「哪些页面会随数据量增长」。

已经把详情页补进那套测试。变异测试确认咬得住：

```
AssertionError: /tournaments/626/：3 条数据用了 8 次查询，10 条用了 15 次——查询数随数据量增长，说明有 N+1。
```

## 实测：开放 API（目标 500ms，名单导出除外）

```
  ✓ 报名列表 limit=50                    p95   5.1ms  查询 22  条数 50
  ✓ 报名列表 + 全部展开 limit=50             p95   6.3ms  查询 22  条数 50
  ✓ 报名列表 limit=200（上限）               p95  19.8ms  查询 22  条数 200
  ✓ 赛事名单 roster（200 支队）              p95  16.4ms  查询 22
  ✓ 赛事统计 stats                       p95   2.1ms  查询 24
  ✓ roster.csv（200 支队 1200 人）         p95  14.7ms  查询 22
```

**查询数恒定 22，不随 limit 从 50 涨到 200 而变化**——018 轮的 `prefetch_related` 是对的。

CSV 导出设计里明确排除在 500ms 之外，实测 14.7ms，远没到需要特殊处理的程度。

## 实测：后台和分队算法

```
  ✓ 内战分队页（100 人报名）      p95  10.8ms  查询 10
  ✓ 后台报名审核列表（200 条）     p95   7.8ms  查询 11
  ✓ 从 100 人里选 10 人分队      最慢 24.0ms  中位 23.5ms  目标 1000ms
```

分队页要渲染 100 张卡片，10 次查询；审核列表 200 条，11 次查询。都是恒定的。

## 还是没验证的

- **网络延迟**。服务器在海外、用户在国内，这部分只能真机量，设计 15.1 的「中国大陆用户 3 秒内可用」仍然未验证。
- **并发**。设计假设同时在线 200 人，这轮是单线程顺序请求，没有测并发下的 SQLite 写锁表现。这个值得在试运行时看。
